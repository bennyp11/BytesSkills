# Shared skill execution contract

Use the skill's version-pinned `definitions/skills/<id>.json` when present,
alongside the pinned command and handler. Schema v2 formalizes creative skills;
system commands and skills not yet migrated continue using their operation contracts.
Definitions describe behavior; they are not executable tools or authorization grants.

## Resolve intent and inputs

Natural language and `/bytes` use the same operation, begin/adoption flow,
permissions and persistence. Clarify ambiguous intent; help stays read-only.
Only `interface: flag` inputs describe flags. Conversation fields are intake values,
not newly registered flags. A contract file alone never registers a command.

Follow `intake_order`, `applies_when` and `parameter_rules`. Group alternative
selectors into one question. Required means required when applicable; optional
creative choices can still need clarification under the handler. Skip inapplicable
inputs. Preserve settled context. `inherit_from` names eligible input sources,
not an automatic merge: explicit values override compatible inheritance; conflicting
sources require resolution. Record explicit, inherited, delegated and inapplicable
values and their origins. Defaults are suggestions, not answers. Ask one clarifier
at a time; “idk” delegates only that field. Never delegate fabrication of a pointer
or missing source file.

## Execute and save

Check actual host capabilities for each applicable output before attempting it.
`effects` declares what a skill may need; existing user authorization, host policy,
OAuth scopes and workspace access still control what it may do. External publishing,
purchases and permission expansion are not authorized by this contract.

Artifact type is semantic (`script`, `video`); format is editorial (`reductions`);
media type describes bytes (`text/markdown`, `video/mp4`). Check each selected output's
media types, profile and quality checks. A plan is never a completed video. Do not
invent formats or profiles from their names. Profiles are pinned by ID and version.

Save through the shared runtime with exact input revisions and the run's actual
skill-release provenance. New candidates receive new IDs; updates require the latest
revision and expected_revision. Metadata-only changes reuse existing file content.
Plain `text` saves currently produce Markdown; other file types need verified uploaded
bytes. The current 10 MB upload limit still applies. Do not relabel Markdown as JSON,
PDF or video. Contract validation does not itself validate generated bytes or render files.

Local delivery is allowed only when explicitly declared, requested/authorized, and
reported as local-only. It does not create a cloud video pointer. A remote save failure
never authorizes silently switching the workspace to local storage.

## Finish or recover

Preserve successfully saved outputs on partial failure; mark the run honestly and
explain missing deliverables. An identical save retry reuses request_id and arguments.
A new execution is a new run. On revision conflict, reread and resolve; never force an
overwrite or claim an unconfirmed save succeeded.

Follow `references/responses.md`: actual outcome, readable title/preview, real pinned
pointer, and independently copyable follow-up commands with known values substituted.
Explain what each command does (for example, “Open this revision”). Suggestions do
not execute themselves. Never show template IDs as saved artifacts.
